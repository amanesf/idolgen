# バトルシステム再設計 検討メモ（未確定・検討中）

このドキュメントは、現行のタクティカル・ライブシステム（`js/battle.js` / `js/battleView.js`）を
再設計するにあたっての検討ログ。まだ実装には入っていない。GDD本体（`GDD_final.md`）を
上書きする前段階のワーキングメモとして残す。

## 0. きっかけ・要望（ユーザー原文ベース）

1. **① 視覚的に属性の効果が分かりづらい**。観客・審査員・関係者のような「攻撃対象」を表現し、
   ダメージが入るようにしたい。属性ごとに全体攻撃／範囲攻撃／狙い撃ちなどの違いを出す。
   → バトル方式そのものを変える話。パズル要素・事前の戦略立案も欲しい。**今回はここを重点的に検討する。**
2. ② バトル中にキャラが喋る（小さい吹き出し）→ 後回し
3. ③ クォータービュー化・キャラアイコン表示 → 後回し

## 1. 現状分析（再設計前の仕様）

- アイドル側は「送る／耐える」の2択のみで攻撃という概念がなく、属性は自分の得点効率・消耗への
  バフとしてのみ機能していた（客席・審査員への攻撃という表現が一切ない）。
- 一方で被弾側（`DAMAGE_PATTERNS`）にはすでに `targeting: random / all_exposed / lowest_stamina /
  center / anti_trend / random_multi` という「全体・範囲・狙い撃ち」の語彙が実装済みだった。
- つまり「客側が一方的にアイドルを攻撃してくる」非対称構造になっており、得点行為が何にも
  "作用"していないのが分かりにくさの根源、と整理した。

## 2. 合意した設計コンセプト

### 2.1 客席ボード（新設・スコアの置き換え）

抽象的な `targetScore` を廃止し、**客席ボード**（観客セクション・審査員席・スタッフ列などの
ブロックの集合、各ブロックがHPを持つ）に完全に置き換える。データ形状は既存 `FORMATIONS` の
スロット定義（id/label/x/y）を踏襲し、`maxHp` を足すだけで済む設計。

### 2.2 パズル要素の置き所

ターン中に「どのブロックを狙うか」をプレイヤーに毎ターン選ばせる操作は**追加しない**。
狙い先は「スロット位置×属性」で自動決定し、戦略性は**事前編成（誰をどのスロットに置くか）**
に一本化する。テンポの良さ（1曲5〜10秒の演出）を壊さないための判断。

### 2.3 被弾（スタミナ消耗）の位置づけ

既存の `DAMAGE_PATTERNS` は「客席・審査員からの反撃」として再解釈する。攻撃（客→客席）と
防御（客席→アイドル）を同じ語彙（全体・範囲・狙い撃ち）で語れるようにし、UIの一貫性を出す。

### 2.4 事前戦略

`loadout.js`（編成画面）にそのステージの客席ボード配置（会場特性）のプレビューを追加し、
「この現場は審査員狙い撃ちが刺さる」等が編成前に読めるようにする。

## 3. 属性システムの再設計（複数回の反復で以下に収束）

### 3.1 経緯（簡略）

1. 最初は属性ごとに個別の計算式（10属性バラバラ）→ 複雑すぎるとの指摘。
2. 「攻撃の形」×「連動ステータス」の2軸に単純化する案 → まだ複雑との指摘。
3. 「役割（アタッカー／ディフェンダー／サポーター）」と「攻撃の形」を分離、
   両方こなす「オールラウンダー」枠を追加。
4. 攻撃の形を6種に拡張（狙い撃ち・範囲・全体・貫通・連続・遠距離）。既存の陣形（前列/後列、
   露出中/非露出）と絡められる「遠距離」（非露出スロットからでも攻撃できる）を追加。
5. 属性を10→14に拡張（ディフェンダー+1・サポーター+1・オールラウンダー+2）。
6. アイコン重複を解消（オールラウンダーの役割アイコンとレインボー属性の🌈重複、
   「全体」形と🌊波属性の重複）。
7. 属性名（自然モチーフ）と攻撃の形の意味的つながりを再検討
   （例: 🌙陰＝遠くから照らす月→遠距離、🌊波＝寄せては返す→連続）。
8. **さらに簡素化の方向へ転換**: 「形」「役割ごとの効果種別（軽減/身代わり/反撃/バフ/回復/鼓舞）」
   といった個性は**属性から特能（talent）側に移す**。属性側は「攻撃／防御／回復」の
   **3軸の強さプロファイルだけ**を持つシンプルな数値データにする。
   - 特能は既存の `talent` 抽選（スカウト時の低確率レア枠）に統合し、属性に応じて
     出現しやすい特能の傾向を持たせる（重みづけ抽選）想定。**特能側の一覧はまだ未確定。**
9. 3軸の表現方法を 大/中/小/なし → 0〜3 → 1〜5 と改訂。攻撃は「なし」を作らない
   （攻撃0だと編成によってはクリア不能になるため、最低値を保証する）というルールを
   ユーザーが明示。最終的に **1〜5の5段階（無しは廃止）** に統一。
10. レア度も同様に1〜5の5段階にし、レア度が上がるほど3軸合計値も緩やかに上がる
    ピラミッド分布（★1が最も出現しやすい前提）にした。

攻撃/防御/回復は1〜5の5段階（「なし」は廃止、攻撃は最低2を保証）。5(最大値)は
レア度が上がるほど出現しやすくなるよう意図的に絞ってあり、合計値もレア度ごとに
帯が重ならず必ず上のレア度が上回る（★1=6〜7 / ★2=8〜9 / ★3=10 / ★4=11 / ★5=12〜13）。

| ★1 | 🗿岩 | 2 | 4 | 1 | 7 | 5なし |

| ★3 | 🌙陰 | 3 | 4 | 3 | 10 | 5なし |

## 4. 特性（トレイト）システム（検討開始）

属性の3軸プロファイル（3.2節）に加えて、以下の3種・計46個の「特性」を持たせる方針で検討中。
攻撃の形（狙い撃ち・範囲・全体・貫通・連続・遠距離）や、防御/回復/バフ寄りの個性
（反撃・身代わり・鼓舞など）は、ここに集約する。

1. **属性特性（14個）**: 各属性ごとに固定で1つ持つ、その属性のアイデンティティを表す特性
   （ランダム抽選ではなく、その属性なら必ず持つ）。
2. **プラス特性（16個）**: キャラクター単位でランダムに抽選される、プラスの個性（既存の
   `talentEffects`：`stage_strong` / `mood_maker` 等はここに統合）。
3. **マイナス特性（16個）**: キャラクター単位でランダムに抽選される、マイナスの個性
   （既存の `glass_throat` はここに統合）。デメリットを持たせることでスカウトの当たり外れに
   バリエーションを出す。

## 5. バトル画面設計（ワイヤーフレーム検討）

HTMLモックアップを作成して画面構成を検討した（Artifact: 客席ボード×陣形パズルのワイヤーフレーム）。
以下は確定した画面レイアウト方針。

### 5.1 画面の縦構成

上から: トップバー（ステージ名・客席HP合計ゲージ）→ **舞台（陣形・アイドル側）** →
**客席ボード（3×3）** → 予兆・ログ → アクションバー（耐える/送る/撤退）。

- **アイドルが上、客席ボードが下**（カメラ/操作ボタンに近い側）で確定。
  理由: カメラは客席側にいて、奥のステージにいるアイドル達がこちらを向いて演じている、
  という向きにすることで、アイドルが正面を向いた状態が自然に成立する（クォータービューで
  アイドルが後ろ向きになる問題を回避）。操作ボタン直上に客席ボードがあるので、
  「送る/耐える」の結果が客席HPにどう効いたかもすぐ確認できる。
- 客席ボード(3×3)は 審査員列(狙い撃ち向け・高HP) / 客席列(範囲向け・中HP) /
  関係者列(中継クルー・SNS実況勢・常連ファンなど、全体向け・低HP) の3行構成。
- 攻撃の形（狙い撃ち/範囲/全体など）は、アイドル→客席ブロックへの線・扇形のSVGオーバーレイで
  可視化する（①の核心である「属性の効果を視覚的に分かりやすくする」に直結）。
- フォーメーションの陣形は、既存の「V字コンベア」ならセンターが客席に一番近い最前列
  （V字の頂点が客席側）になるよう配置する。頂点が奥を向く「逆V字」は別の陣形パターンとして
  後日検討。

### 5.2 ③ 顔アイコン（クォータービュー内のキャラ表示）

`js/scoutGenerator.js` でスカウト時に確定する `idol.portrait`（`sheetFile`/`row`/`col`/`cellSize`）
という実在の顔画像データがすでにあり、`idolDetailView.js` の `drawPortrait` で
canvas描画＋`portraitPaintFilter.js` の厚塗りフィルターをかけて表示している。バトル画面でも
これをそのまま流用する方針。

- 描画ロジックを共通ヘルパー化（例: `portraitPaintFilter.js` に `drawPortraitToCanvas()` を切り出し、
  `idolDetailView.js` と `battleView.js` の両方から呼ぶ）し、40px程度の小サイズで丸くマスクして使う。
- 属性アイコン・ロールアイコンは顔とは別に、チップの左上/右下に小バッジとして独立させる
  （顔＝キャラの個性、バッジ＝ゲーム上の役割情報、と役割を分離）。
- 客席ボードの各ブロック（審査員・客席・スタッフ）は個別キャラではない集団枠なので、
  ポートレートは使わず絵文字アイコンのままでよい。
- `idol.portrait` が無い場合は既存の `avatarHtml`（色相+イニシャル）にフォールバック
  （`idolDetailView.js` と同じガード）。

### 5.3 ② 吹き出し（バトル中のセリフ表示）

既存の `resolveTurn()` が返す `events` 配列（`battle.js`）に相乗りさせ、`battleView.js` の
`handleEvent` に `speech` ケースを1つ追加するだけで実装できる構造にする。

- **発生タイミング**: 1ターンにつき最大1〜2体だけ発話（全員分出すと煩雑になるため）。
  優先度は「強制引退 > 大ダメージ被弾 > 大きいスコア獲得 > その他」の順で該当者を抽選。
- **せりふの中身**: `masterData.js` に `BATTLE_LINES` のような辞書を追加し、
  イベント種別×属性/ロール/特性で引く（例: ⚔️アタッカーの得点時「見てて、これが本気!」、
  🛡ディフェンダーが軽減した時「私が壁になる!」、💚サポーターの回復時「まだいける、頑張ろ!」、
  被弾時の共通セリフ数パターン、強制引退時のお別れの一言）。特能持ちは専用の一言を1つ持たせる。
- **表示ルール**: チップ真上にポップし1.5〜2秒でフェードアウト。同時発話は前述の抽選で
  最大1〜2体に制限し、吹き出し同士が重ならないようにする。
- **データフロー**: `resolveTurn()` に `{ type: "speech", idolId, line }` イベントを追加 →
  `battleView.js` の `handleEvent` switchに1ケース追加。既存のイベント順次再生アーキテクチャに
  そのまま乗る。

## 6. 実装状況（Phase 1: 客席ボード×属性の3軸プロファイル、実装済み）

ここまでの検討をコードに落とし込んだ。

- **`js/masterData.js`**: `ATTRIBUTES`を14属性（role/rarity/atk/def/heal/shape/effect/traitLabel）
  に置き換え、`ATTACK_SHAPES`（攻撃の形6種）・`AUDIENCE_BOARD_BLOCKS`（客席ボード3×3の
  レイアウト）を新設。旧`BALANCE.attributeEffects`（属性ごとの個別係数）は廃止し、
  `BALANCE.attributeScaling`（atk/def/healを効果量に変換する共通係数）に統合。
  `TALENTS`をプラス16・マイナス16の計32個に拡張（`kind`フィールドで区別）。バトルに
  関わるもの11個（大舞台○・ムードメーカー・負けず嫌い・天性のセンター・根性・ガラスの喉・
  あがり症・センター恐怖症・燃え尽き症候群・マイペース・打たれ弱い）は`talentEffects`に
  実装済み。残り21個（経営/育成/加齢に関わるもの）はラベル・説明文のみのカタログで、

## 9. 実装状況（Phase 4: 特性32個中30個を実装済み）

残っていた特性のうち、実在するシステムに素直に接続できるものを実装した。

- **`js/training.js`**: 練習の虫/練習嫌い(開示度の伸び)、不器用/早熟/一点集中(成長量)、
  早熟の反動(成長上限が85で頭打ち)。`bestStatKey()`ヘルパーを追加。
  `applyTraining`の呼び出し側は`idol.age`が必須になった点に注意。
- **`js/scoutGenerator.js`**: 幸運体質(在籍人数分だけ掘り出し物確率を底上げ)。
- **`js/state.js`**: 人気者(成功時、出演していた人数分だけファンの伸びを上乗せ)。

32個中30個が実際に効果を持つ。残り2つ(**大器晩成**・**大厄年**)は「年齢による
ステータスの経年増減」という土台のシステム自体がまだ無い(既存のAGE_BANDSは
あくまで陣形パズル上の係数で、ステータス数値そのものを動かす仕組みではない)ため、
ラベル・説明文のみのカタログのまま残した。この2つを実装するには年齢によるステータス
変動の仕組み自体を新設する必要があり、範囲が広いので別途相談してから着手する。

シミュレーションで32特性すべてを実際にバトル→報酬計算→育成まで通し、エラーなく
動作することを確認済み。

## 11. 実装状況（Phase 6: 年齢-ステータス増減システム、実装済み・特性32/32完了）

`BALANCE.aging`(新設)と`state.js`の`applyAging()`で、`advanceDay()`ごとに以下を判定する。

- **経年劣化**: バフの司令塔世代(22歳〜)は1ステータスにつき`declineChancePerStatPerDay`
  (2%)の確率で毎日-1、`declineFloor`(20)を下限に下げ止まる。特能「大器晩成」は
  この確率を`declineChanceMultiplier`(0.35倍)に抑える。
- **大厄年**: 低確率(通常1%/日、特能「大厄年」保持者は10%/日)で発生し、発生すると
  そのステータスを`statDropPercent`(12%)だけ一時的に下げる。`idol.statDebuff`に
  減少量と`expiresOnDay`を記録しておき、`durationDays`(3日)経過後に自動で元の値へ
  正確に戻す(四捨五入の丸め誤差が出ないよう、下げた分をそのまま加算し直す)。
- `idolDetailView.js`にデバフ中を示す「😷 大厄年で一時的に低下中」タグを追加。
- シミュレーションで300日分回し、大器晩成/通常/大厄年保持者で減衰量に有意差が出ること、
  デバフが3日後に正確に元へ戻ることを確認済み。

これで特性32個すべてに実際の効果が入った。

## 13. 実装状況（Phase 8: 全画面スクロール禁止に対応）

バトル画面だけでなく、アプリ全体を「一切スクロールしない」固定ビューポート設計に変更した。

  `.list-row`(コンパクト1行)、`.pagination`、`.screen-header-row`を新設。
- **`js/ui.js`**: `paginate()`(件数不定の配列を固定件数ずつ切り出す)、`paginationHtml()`、
